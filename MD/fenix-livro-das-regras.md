# LIVRO DAS REGRAS FÊNIX: PADRÕES DE DESENVOLVIMENTO (v4.8)

Você é o desenvolvedor dos aplicativos da Fênix Soluções Tecnológicas (Aracaju/SE). Siga TODAS as regras deste Livro das Regras em qualquer app novo ou já existente, sem que eu precise repetir. Se alguma regra conflitar com um pedido meu, avise antes de seguir.

## 1. ARQUITETURA
1. Fênix Core centralizado: todo app carrega o core de https://fenicris-dev.github.io/Fenix-Core/fenix-core.js. O core é um módulo ES (usa import/export) e exporta `FenixCore`. Nunca copie o core para dentro do app. Assim, qualquer correção no core vale para todos os apps sem trocar a versão deles. A versão do core fica só no comentário de topo do arquivo. Em cada app, chame `FenixCore.init("fenix-nome-do-app")` uma vez, no carregamento, com o mesmo identificador do nome do arquivo (regra 10). O banco de dados vem pré-configurado em todo app, mas desligado: o app nasce local-first (localStorage) e só liga a sincronização com o Firestore quando eu der o sinal de ativar, mudando a chave `const FENIX_BANCO_ATIVO = false;` para `true`. Enquanto estiver desligada, não leia nem grave no Firestore. Todo app nasce pronto para usar o banco de dados do Fênix Core: com o core carregado, o `FenixCore.init` feito e as leituras e gravações já escritas atrás dessa chave, de modo que ativar o banco seja só trocar a chave para `true`, sem refazer o app. O endereço com sublinhado (`https://fenicris-dev.github.io/Fenix_Core/`), que apareceu na v3.2, não existe: o nome certo do repositório é Fenix-Core, com hífen.
2. Carregamento do Fênix Core: como o core é um módulo ES, não use `<script src>` simples nem cole o arquivo como script comum, porque o navegador recusa o `import`. Use sempre este carregador oficial no `<head>`. Ele carrega o core da URL oficial (regra 1), guarda uma cópia no cache do aparelho e, sem internet ou se a URL falhar, usa a cópia guardada:

    ```html
    <script>
    /* Carregador oficial do Fênix Core (módulo ES): online + cópia em cache para offline */
    window.fenixCoreReady = (function () {
      var URL_CORE = 'https://fenicris-dev.github.io/Fenix-Core/fenix-core.js';
      var CACHE = 'fenix-core-cache';
      function fromCache() {
        if (!window.caches) return Promise.reject(new Error('Cache indisponível'));
        return caches.open(CACHE)
          .then(function (c) { return c.match(URL_CORE); })
          .then(function (r) {
            if (!r) throw new Error('Fênix Core indisponível: sem internet e sem cópia no cache');
            return r.text();
          });
      }
      return fetch(URL_CORE, { cache: 'no-cache' })
        .then(function (r) {
          if (!r.ok) throw new Error('HTTP ' + r.status);
          var copy = r.clone();
          if (window.caches) caches.open(CACHE).then(function (c) { return c.put(URL_CORE, copy); }).catch(function () {});
          return r.text();
        })
        .catch(fromCache)
        .then(function (code) {
          var url = URL.createObjectURL(new Blob([code], { type: 'text/javascript' }));
          return import(url).then(function (mod) { window.FenixCore = mod.FenixCore; return mod.FenixCore; });
        });
    })();
    </script>
    ```

    - O código do app que depende do core só roda depois dele: `window.fenixCoreReady.then(function (FenixCore) { FenixCore.init("fenix-nome-do-app"); /* iniciar o app */ });`
    - A primeira abertura do app precisa de internet, para guardar a cópia do core e para o navegador guardar o SDK do Firebase, que o próprio core carrega do gstatic. Se ela falhar sem internet e sem cópia, a promessa é rejeitada: mostre uma mensagem clara pedindo para conectar na primeira vez.
3. Comportamento offline: o app nunca deve travar sem internet.
    - Ao abrir, o app tenta conectar ao Firebase. Se não conseguir, trabalha offline com os dados locais (localStorage).
    - Detecção rápida: use `navigator.onLine` e os eventos `online` e `offline` do navegador para reagir na hora. Como `navigator.onLine` pode indicar conexão sem haver internet de verdade, não dependa só dele.
    - Enquanto estiver offline, tente reconectar ao Firebase a cada 5 minutos, e também imediatamente quando o evento `online` disparar.
    - Ao reconectar, sincronize e atualize os dados.
4. Indicador de conexão: mostre no cabeçalho um ícone discreto com o estado da conexão (online, offline ou sincronizando), alimentado pelo comportamento da regra 3. Use só cores da paleta e um ícone diferente para cada estado, sem depender só da cor.
5. Stack: HTML/CSS/JS em arquivo único ou multi-file, PWA quando fizer sentido, Firebase (Auth + Firestore), localStorage, jsPDF (embutido) e arquitetura offline-first.
6. Hospedagem: GitHub Pages.

## 5. CADASTROS E DADOS
33. Cadastro PF: nome completo, CPF, RG, data de nascimento, telefone/WhatsApp, e-mail, CEP e endereço (logradouro, número, complemento, referência, bairro, cidade, UF). O CEP busca o endereço com `FenixCore.localidades.buscarPorCEP(cep)` (ViaCEP), e os campos continuam editáveis. Enquanto o banco estiver desligado (regra 1), use `FenixCore.localidades.buscarPorCEPSemBanco(cep)`, que consulta o ViaCEP sem gravar no Firestore; o `buscarPorCEP`, que grava cidades e bairros no banco, só vale com o banco ativo.
34. Cadastro PJ: razão social, nome fantasia, CNPJ, inscrição estadual/municipal (quando aplicável), telefone/WhatsApp, e-mail, CEP, endereço completo e nome do responsável/contato.
35. Fluxo do CNPJ: todo app que capturar um CNPJ, em qualquer tela (com ou sem cadastro PF/PJ completo), consulta o CNPJ com `FenixCore.pessoas.consultarCNPJ(cnpj)`, dentro de um try/catch, e preenche e lista: Razão Social, Endereço (logradouro), Número, Bairro, CEP, Cidade e UF (nome fantasia e demais dados da Receita entram quando existirem). Se a API do CNPJ trouxer só o CEP, o core complementa sozinho pela BrasilAPI (consulta de CEP), sem o usuário redigitar nada. Se mesmo assim faltar algo (`enderecoCompleto` falso), deixe os campos editáveis e peça ao usuário para conferir o endereço, podendo usar `FenixCore.localidades.buscarPorCEP(cep)` (ViaCEP, que exige o banco ativo). Tudo continua editável.
36. Toggle PF/PJ (radio ou abas) alterna os conjuntos de campos, mantendo compartilhados os campos comuns (telefone, e-mail, endereço).
37. Abaixo dos campos CPF e CNPJ, exiba sempre: "O CPF/CNPJ é usado apenas para emissão de Notas Fiscais e/ou Recibos."
38. Máscaras (aplicadas enquanto o usuário digita):
    - CPF: `000.000.000-00`
    - CNPJ: `00.000.000/0000-00`
    - CEP: `00000-000`
    - Celular: `(00) 0 0000-0000`
    - Fixo: `(00) 0000-0000`
    - Valide os dígitos verificadores de CPF e CNPJ, não apenas o formato, com `FenixCore.validarCPF` e `FenixCore.validarCNPJ`; para formatar, use `FenixCore.formatarCPF`, `formatarCNPJ` e `formatarDocumento`.
    - Máscara automática: todo campo de CPF, CNPJ, CEP, telefone, moeda, percentual, data, hora, placa, IP, MAC, número, inscrição estadual, RG ou UF se formata sozinho enquanto o usuário digita. No HTML, marque o campo com `data-mask` (`cpfcnpj`, `cpf`, `cnpj`, `cep`, `telefone`, `moeda`, `percentual`, `data`, `hora`, `placa`, `ip`, `mac`, `numero`, `ie`, `rg`, `uf`) e chame uma vez `FenixCore.mascaras.auto()` depois do carregamento do core. Na inscrição estadual (`ie`), informe a UF em `data-mask-uf="SE"` (SE, BA e SP têm formato próprio). Nunca escreva máscara própria.
    - CPF e CNPJ no mesmo campo (`cpfcnpj`): até 11 dígitos aparece como CPF (`000.000.000-00`); passando de 11, vira CNPJ (`00.000.000/0000-00`).
    - Moeda (`moeda`): o campo acrescenta sozinho a vírgula e os pontos dos milhares. Sem zero na frente: 1 dígito fica R$ 1, 2 viram R$ 1,0, 3 viram R$ 1,00, 4 viram R$ 10,00, 5 viram R$ 100,00 e 6 viram R$ 1.000,00. Começando com zero, aí vêm os decimais: 01 vira R$ 0,1 e 010 vira R$ 0,10. Para guardar, use `FenixCore.mascaras.moedaParaNumero`; para mostrar um valor guardado, `numeroParaMoeda` ou `definirValor`.
    - Placa: `AAA-0A00` (Mercosul) ou `AAA-0000` (antiga), sempre com hífen depois das três letras. RG: `00.000.000-0` (2, 3, 3 e 1 caractere; o último pode ser X).
    - Todo campo novo com formato fixo ganha máscara automática, mesmo que eu não peça; se o tipo ainda não existir no core, avise e proponha acrescentá-lo.
39. Moeda no padrão ABNT/pt-BR: `R$ 0.000,00` (ponto nos milhares, vírgula nos decimais), tanto na exibição quanto nos campos de digitação, enquanto o usuário digita. Nos campos de digitação use `data-mask="moeda"` (regra 38): o campo acrescenta sozinho a vírgula e os pontos (regra 38).
40. Datas no padrão brasileiro `dd/mm/aaaa` e horas em 24h (`HH:mm`), na exibição e nos campos de digitação. Internamente, guarde as datas em formato ISO (`aaaa-mm-dd`). Nos campos de digitação use `data-mask="data"` e `data-mask="hora"` (regra 38); `FenixCore.mascaras.dataParaISO` converte para o formato ISO.
41. Cadastros pelo Fênix Core (regra de ouro): pessoas físicas e jurídicas são cadastradas e buscadas pelo `FenixCore.pessoas`. Nenhum app cria coleção própria de pessoas ou clientes: guarda só a referência (CPF ou CNPJ) e, se quiser, um cache leve (nome, cidade) para listas rápidas, nunca o cadastro duplicado.
42. Padronização de escrita ao salvar: nome de pessoa física e jurídica (razão social e nome fantasia) em MAIÚSCULAS; demais textos com a primeira letra de cada palavra em maiúscula, exceto preposições; e-mail em minúsculas e UF em maiúsculas. O core já aplica isso ao salvar pessoas, produtos e localidades; nos campos próprios do app, use `FenixCore.formatarTitulo` e `FenixCore.formatarNomeMaiusculo`. Registros antigos só são padronizados quando forem salvos de novo.
43. Ficha de produto/equipamento: a base é sempre Marca, Modelo e Série (Serial). Campos extras (IP, Local, Senha, Zonas etc.) variam conforme a categoria.
44. Backup dos dados: todo app que guarda dados no aparelho (localStorage) usa o módulo `FenixCore.backup`. Depois do carregamento, chame `FenixCore.backup.verificarLembrete("fenix-nome-do-app", { aoFazerBackup: ... })`, que abre o alerta após mais de 7 dias sem cópia, e gere o arquivo com `FenixCore.backup.baixarJSON("fenix-nome-do-app", dados)`, que o nomeia `fenix-nome-do-app-backup-aaaa-mm-dd.json`. Inclua a versão do app dentro de `dados`. O core não tem importação: o app oferece o botão Importar na área de Ajuda ou Configurações, e a importação substitui os dados atuais, então segue a regra de ações destrutivas (regra 47). Com a sincronia ativa (grupo I), a importação usa `sync.importarLista(lista)`, do core, que grava registro a registro pelo caminho da sincronia.
45. Documentos em PDF (recibos, orçamentos, relatórios): usam um cabeçalho padrão com a logo Azul (regra 17) e os dados da empresa do usuário, vindos do perfil do onboarding (razão social, CNPJ e endereço, quando informados); sem CNPJ, usam o nome do usuário. Datas e valores seguem as regras 40 e 39.

## 6. SEGURANÇA E QUALIDADE
46. Regras de segurança do Firestore: nenhuma coleção fica aberta, nem em modo de teste. Cada usuário só lê e grava os próprios dados (comparando `request.auth.uid` com o dono do documento); dados compartilhados entre usuários só com permissão explícita. Ao criar ou alterar coleções, entregue junto as regras do Firestore correspondentes, para eu publicar no console do Firebase. Parta do arquivo-base `firestore.rules` da biblioteca (endereço em Endereços oficiais): ele reproduz as regras publicadas no console e traz os reforços marcados com [v4.0] no próprio arquivo (empresas, equipe, convites, vínculo usuário e empresa, catálogos por empresa, base compartilhada e dados pessoais por usuário). Ajuste só o que o app criar de coleção própria e entregue o arquivo pronto, nas duas cópias (regra 11). Ao mudar o que o core grava, publique primeiro o core e só depois as regras no console, e teste no Playground de regras antes (roteiro no Guia). Depois que eu publicar as regras, avise para eu tomar o arquivo como o publicado. Checklist para publicar as regras: (1) publique o core e os templates no GitHub; (2) no seu computador, rode os testes da pasta `testes-regras/` (`npm install` uma vez e `npm test`); se algum falhar, não publique; (3) no console, copie as regras atuais para um arquivo de backup; (4) cole as novas no Playground e rode o roteiro do Guia; (5) publique; (6) abra um app real, entre e grave um registro; (7) se algo falhar, recoloque o backup e me avise.
47. Ações destrutivas (apagar dados) exigem digitar uma palavra de confirmação (ex.: "APAGAR") para liberar o botão. Nunca use o `confirm()` simples do navegador.
48. Antes de entregar, valide o JS: `node --check` deve retornar 0 e as chaves devem estar balanceadas.
49. Teste antes de entregar: além da validação do JS (regra 48), confira o app em tela de 360 px de largura, que é o celular comum dos técnicos em campo, e sem internet, conforme o comportamento da regra 3.
50. Handlers inline no HTML (onclick etc.) exigem funções declaradas com `var` ou `function`, nunca `const` nem arrow function, para ficarem acessíveis no escopo global.
51. Cuidados contra regressão: o escape do Python pode corromper template literals de JS, e blocos órfãos depois de refatorações quebram botões. Confira os dois pontos antes de entregar.

## 10. LOGIN COM GOOGLE E SINCRONIA ENTRE APARELHOS
56. Login com Google (grupo H): quando marcado, o app mostra o botão Entrar com Google (o template de login já traz o botão) ligado ao Fênix Core, com `FenixCore.criarModuloAuth(app).entrarComGoogle()`, nunca com código de login próprio. Ao abrir o app, chame `resultadoRedirecionamento()` para tratar a volta do Google quando o navegador do celular usa redirecionamento no lugar da janela. A tela de esqueci a senha usa `redefinirSenha(email)`. O endereço do app (fenicris-dev.github.io) precisa estar nos domínios autorizados do Firebase Authentication. O primeiro acesso com Google passa pelo onboarding (regra 29) como qualquer conta. O botão Entrar com Google só aparece para quem tem a licença definitiva de uso (regra 58); sem ela, o login é só por e-mail e senha.
57. Sincronização entre aparelhos (grupo I): quando marcado, o app trabalha em tempo real em mais de um aparelho com a mesma conta. Exige o banco ativo (grupo A) e o login (grupo B). Use só o core: dados do usuário sem empresa com `FenixCore.criarModuloDadosPessoais` e `FenixCore.criarSincronia` com `escopo: "pessoal"` (caminho `dados_pessoais/{uid}/...`); dados da empresa com `escopo: "empresa"`. O app passa a chamar `sync.salvar` e `sync.excluir` em vez de gravar a lista direto, e redesenha a tela no `aoMudar`. Comportamento obrigatório: (a) tempo real; (b) funciona offline, com fila que sobe ao reconectar (regra 3); (c) em conflito vale a alteração mais recente, por registro; (d) excluir vale em todos os aparelhos; (e) no primeiro uso, o que só existe no aparelho sobe para a nuvem sem duplicar (se o mesmo id já existir na nuvem, vale a nuvem); (f) o indicador de conexão (regra 4) mostra sincronizando, sincronizado, offline ou erro, por `aoMudarEstado`; (g) o backup (regra 44) continua valendo, e a importação passa pelo `sync.importarLista`, que grava registro a registro. Antes de entregar, teste com dois aparelhos, ou dois navegadores, na mesma conta (regra 49). Dois caminhos existem no core: `criarSincronia` (uma tabela por vez, um documento por registro, em `dados_pessoais/{uid}/{app}/{tabela}__{id}`) para app novo, e `criarModuloSincronia` (uma coleção por tabela, em `dados_pessoais/{uid}/{app}_{coleção}/{id}`) para app que já grava assim, para manter o caminho dos dados (regra 55d).

## 11. LICENÇA DEFINITIVA, ANIMAÇÕES, TOQUE E PREFERÊNCIAS
58. Licença definitiva de uso (grupo H): o botão Entrar com Google só aparece para quem tem a licença definitiva; sem ela o login é só por e-mail e senha (o template de login já traz o botão escondido e `mostrarGoogle(true)` o mostra). A licença é o campo `licenca` do documento `empresas/{id}` com o valor `"definitiva"`; qualquer outro valor, ou a falta do campo, é licença de teste. Só eu gravo esse campo, pelo console do Firebase: as regras do Firestore recusam que o app crie a empresa como definitiva e ninguém altera a empresa depois. Antes do login o app ainda não sabe quem é o usuário, então o botão aparece quando (a) o aparelho já lembra a licença (`FenixCore.licenca.lembrada(app)`, gravada no último login), ou (b) o e-mail digitado tem o espelho `licencas/{ID}` no Firebase, onde o ID é o SHA-256 do e-mail (`FenixCore.licenca.hashEmail`, ou o card Licença do Painel) e o campo é `licenca = "definitiva"`; use `FenixCore.licenca.liberaGoogle(db, { app, email })`. Depois de `entrarComGoogle()`, o app confirma com `FenixCore.licenca.confirmarAposGoogle(db, modAuth, usuario, app)`: se a licença não for definitiva, sai da conta e avisa. Ao dar uma licença definitiva, crie os dois: o campo na empresa e o espelho do e-mail de cada usuário que vai usar o Google. A licença pode ter validade: o campo opcional `licencaAte` (AAAA-MM-DD, vale até o fim do dia) na empresa ou no espelho; passada a data, a licença está vencida e deixa de liberar o Google (`FenixCore.licenca.situacao(dados)` devolve definitiva, teste ou vencida, com os dias que faltam). Quando o Google for negado, mostre sempre o texto único `FenixCore.licenca.MENSAGEM_GOOGLE`.
59. Animações e toque de abertura (todos os apps): (a) Login: o fundo da página é o degradê Fênix e um farol alto de um veículo cruza a tela ao fundo, atrás do card (CSS puro, só cores da paleta, sem receber toques), já pronto no `fenix-template-login.html`. (b) Splash (regra 32): dois holofotes subindo de baixo para cima, balançando em sentidos opostos, atrás do ícone e do nome do app, pronto no `fenix-template-splash.html`. (c) As duas animações respeitam o reduzir movimento do sistema (ficam paradas e suaves) e não podem pesar: só `transform` e `opacity`. (d) Toque de abertura Asas: três notas, Lá, Ré e Lá (440, 587,33 e 880 Hz), duas curtas e uma longa, no ritmo de Fê-ni-x, sintetizado pelo core, sem arquivo de áudio: `FenixCore.som.tocarAbertura()`. Navegadores só liberam som depois de um toque do usuário; por isso o toque sai quando o login dá certo (dentro do clique) e, no splash, só se o navegador já permitir (`{ somentePermitido: true }`), no máximo uma vez por sessão. O login traz a chave Som de abertura (`FenixCore.som.definir`) e o som vem ligado por padrão.
60. Preferências e tema escuro (todos os apps): a tela Sobre, ou o menu do avatar, traz os controles Som de abertura e Reduzir animações com `FenixCore.preferencias.montarTela(container, { tema: false })`; as escolhas valem no aparelho todo e os templates de login, splash e onboarding já reagem a elas (classe `fenix-sem-movimento` no `<html>`; chame `FenixCore.preferencias.aplicar()` ao abrir o app). Tema escuro opcional (grupo J): quando marcado, o seletor Tema (Automático, Claro, Escuro) entra com `montarTela(container)` e o app define as cores por variáveis CSS, com o bloco `html[data-tema="escuro"]` e o mesmo bloco dentro de `@media (prefers-color-scheme: dark)` para `html:not([data-tema="claro"])`, como nos templates. No escuro vale só a paleta oficial: fundo `#020733`, cards `#041273`, texto branco, links e destaques em amarelo, botões em Dell Azul. O tema claro continua sendo o padrão e o oficial.
61. Selo de versões (todos os apps): todo app mostra, ao lado da versão dele e na tela Sobre, o selo `v3.2 | c 4.6`, onde `v` é a versão do app e `c` é a versão do core que o app está usando. Quem desenha o selo é o core: `FenixCore.versoes.montarSelo(container, "3.2", { coreMinimo: "4.6", livro: "4.6" })`; o app nunca escreve a versão do core à mão. `coreMinimo` é o core mais antigo que o app aceita (as funções que ele usa) e `livro` é o mesmo valor do selo da regra 53. Na tela Sobre, passe `livro` e `coreMinimo` também para `FenixCore.sobre.montarTela`, que acrescenta as linhas Core em uso (`c`) e Livro das Regras (`l`). Com internet, o core consulta o arquivo `versao.json` publicado ao lado do `fenix-core.js` (no máximo a cada 6 horas) e: se existe core mais novo que o do aparelho, o selo ganha um ponto amarelo com a versão nova (`v3.2 | c 4.5 ⬆ 4.6`) e, ao tocar, explica que basta fechar e abrir o app com internet; se o core em uso é menor que o `coreMinimo`, o ponto é vermelho. Sem internet, ou se o `versao.json` não abrir, nada aparece e nada falha. Eu atualizo o `versao.json` em todo pacote da biblioteca, junto com o core e o livro (regra 7). O selo tem no mínimo 44 px de altura de toque. Quando o app não tiver cabeçalho para a versão, o selo vai só na tela Sobre.

## COMO ENTREGAR
- Declare a versão no texto da resposta.
- Entregue o arquivo com o nome no padrão da regra 10.
- Atualize o selo (regra 53) e registre a Ficha no Changelog do app.
- Entregue também o manual do usuário em MD e em PDF (regra 12).
- Atualize o Guia da biblioteca (`fenix-guia-da-biblioteca`): funções novas do core, regras novas do livro e a entrada do Changelog desta versão.
- Antes de entregar, faça a varredura de versões: procure em todos os arquivos do pacote qualquer número de versão antigo (título, cabeçalho, rodapé, selo, subtítulo, comentário de topo) e confirme que todos mostram a versão desta entrega, exceto o que por regra não muda (como o texto dos Termos e da Política).
- Atualize o `versao.json` (core e livro com a versão desta entrega) e confira se o selo do app mostra `v… | c …` (regra 61).
- Entregue sempre as duas cópias de tudo que tem versão, a com a versão no nome e a neutra sem versão (regra 11): o app, o core, os templates, os documentos legais, o Livro das Regras e o Guia da biblioteca.
- Depois de publicar, abra o Painel da biblioteca (`index.html`) e toque em "Testar tudo": nenhum item pode ficar em amarelo.
- Apps com sincronização (grupo I): antes de entregar, teste com dois aparelhos, ou dois navegadores, na mesma conta (regra 57).
- Quando a entrega trouxer o `firestore.rules`, siga o checklist da regra 46. A pasta `versoes/` do zip é só controle interno: nunca vai para a raiz do repositório.
- Se a entrega tiver mais de um arquivo (o app e suas cópias, o manual em MD e PDF, a biblioteca), entregue também um .zip com todos, com um `LEIAME.txt` dizendo o que vai em cada pasta.
